# Threat Model — Code Q&A Agent on Amazon Bedrock AgentCore

## 1. Document control

- **Project:** `sample-code-qa-on-agentcore`
- **Intended publication:** AWS Samples Type 4, non-production educational sample
- **Deployment model:** customer-owned AWS account and Region
- **Review scope:** the new fixed commit produced after synchronizing `ddpie/source-truth` commit `c8214d917271d33c4f27b9a5d5c115a18f2768af`; prior fixed-commit evidence is not reusable
- **Security responsibility:** repository maintainers; vulnerability reporting follows `SECURITY.md`

This document describes the sample as implemented. It does not claim that the architecture is production-ready. Deployers remain responsible for data classification, identity and access management, network design, logging, model/Region approval, and operational response in their own environment.

## 2. System purpose and security objectives

The sample answers read-only questions about source repositories. A Feishu/Lark gateway invokes an agent in an Amazon Bedrock AgentCore session microVM. The agent uses a read-only MCP-over-HTTP bridge on an EC2 index host to retrieve code evidence, then sends the question and selected evidence to an Amazon Bedrock model. The response can include source-derived symbols, snippets, and file paths.

Security objectives:

1. Preserve the read-only product boundary; the agent must not modify repositories or infrastructure.
2. Prevent credentials and unrelated host data from entering model prompts, logs, glossary output, or chat responses.
3. Restrict each project to its declared repositories and prevent path traversal or cross-project reads.
4. Limit bridge reachability to the intended VPC path from AgentCore Runtime.
5. Keep dependency acquisition and build inputs reviewable and reproducible.
6. Make destructive operations explicit, operator-controlled, and excluded from the normal deploy path.
7. Give operators enough telemetry to detect retrieval failure, leakage attempts, and unhealthy infrastructure.

## 3. Data and assets

| Asset | Sensitivity / impact |
| --- | --- |
| Source repositories and index | May contain proprietary source, business logic, identifiers, and accidentally committed secrets; unauthorized disclosure is high impact |
| Feishu/Lark app secret and bot identity | Allows bot impersonation and message access within granted scopes; fetched from Secrets Manager into the gateway process environment and not written to a credential file |
| Read-only Git credential | Allows cloning every repository covered by the credential; fetched from Secrets Manager and written under `umask 077` to `/opt/idx/git-token-${PROJECT_ID}` plus restricted askpass/environment files |
| Telemetry hash salt | Prevents stable user identifiers in logs from being trivially reversible across deployments |
| AgentCore runtime role and EC2 instance role | Grant model invocation and scoped AWS control-plane/data-plane access |
| S3 artifacts and ECR image | Determine code executed on the host and in session microVMs |
| Questions, retrieved excerpts, answers, traces | Can contain source content and user/business context |
| Glossary slices | Derived source metadata served to the agent; could leak secrets if extraction controls fail |
| CloudWatch logs and evaluation traces | Operational evidence that may contain identifiers or source-derived text |

**Data-processing statement:** the repository clone stays on the EC2 index host, but selected source content does not necessarily stay on that host. During Q&A, retrieved excerpts are sent from the AgentCore microVM to the selected Bedrock model. The OpenAI Agents SDK path uses the custom Bedrock adapter and `ConverseStream`; the Claude Agent SDK path invokes Bedrock through the local Claude CLI subprocess. When the optional glossary is enabled, selected repository content is sent to Bedrock from the index host by the project-selected engine: OpenAI Agents SDK through `ConverseStream`, or the exact-pinned Claude Code CLI. Answers and source-derived content are returned to Feishu/Lark. Deploy only repositories, Regions/models, and chat recipients approved for this data.

Optional AgentCore Evaluations reprocess the captured OpenTelemetry/OpenInference spans. LLM-as-judge evaluators receive trace content through the evaluation service; the citation evaluator Lambda reads the repository through the same private bridge; evaluation results are written to CloudWatch Logs/metrics. Apply the same data classification, Region/model approval, access policy, and retention requirements to evaluation inputs and outputs. Keep online evaluation disabled unless live-traffic sampling has been approved.

## 4. Components and data flow

1. A user mentions the bot in Feishu/Lark.
2. `bot-gateway` receives the event over the platform long connection, maps `chatId`/`threadId` to a bounded pool of `runtimeSessionId` values, signs the invoke request with AWS credentials, and streams card updates. New routes borrow idle IDs, create an ID if none is idle and the pool has capacity, or share an existing ID when the pool is full.
3. Each project has a separate AgentCore Runtime, which starts or reuses a microVM for the selected `runtimeSessionId`. `AGENT_SDK` selects OpenAI Agents SDK (new-project default) or Claude Agent SDK; each invocation starts a fresh SDK conversation with explicit replay of the current follow-up chain. The project's gateway process serializes invocations sharing a `runtimeSessionId`.
4. The selected SDK sends read-only MCP requests to the index-service bridge over the VPC. OpenAI registers the same closed HTTP MCP allowlist; Claude receives the restricted MCP configuration.
5. The bridge queries CodeGraph or reads/searches files under declared repository roots and returns bounded evidence.
6. The selected SDK sends the user question and evidence to Bedrock. OpenAI uses `bedrock_converse.py` and `ConverseStream` with SigV4; Claude uses the exact-pinned local CLI with `CLAUDE_CODE_USE_BEDROCK=1`.
7. The gateway applies best-effort sanitization/redaction and returns the source-derived answer to Feishu/Lark.
8. Optional background glossary jobs use the same project SDK selection on the index host: OpenAI Agents SDK with batch-scoped read tools and `ConverseStream`, or the exact-pinned Claude Code CLI. Results are grounded against source and published as read-only slices.
9. Deployment scripts stage artifacts in S3, images in ECR, service credentials in Secrets Manager, and operate the host through Systems Manager. The Git credential is materialized into restricted host files for non-interactive clone/fetch; the Feishu/Lark secret is injected into the gateway process environment.

## 5. Trust boundaries

| Boundary | Control and assumption |
| --- | --- |
| User / Feishu-Lark tenant → gateway | Platform app identity, limited scopes, event validation/deduplication; questions remain untrusted input |
| Gateway → AgentCore Runtime | SigV4 request signed by the EC2 instance role; runtime ARN is configured per project |
| Chats/threads sharing a project runtime pool | Fresh SDK conversations, explicit follow-up replay, and serialization per `runtimeSessionId` in the gateway process control conversation context and invocation ordering. Different chats/threads can reuse the same microVM and `/mnt/workspace`; these are **not per-user or per-chat isolation boundaries**. A fresh SDK conversation does not guarantee clearing reused microVM files or process state |
| AgentCore microVM → index bridge | Private VPC routing and security group; **no application-layer authentication on the bridge** |
| Bridge → repository/index on EC2 | Repository allowlist, path normalization/confinement, withheld-path rules, read-only MCP surface |
| Index host → Bedrock | Instance-role `bedrock:InvokeModel*` permissions for project-selected glossary models; OpenAI uses `ConverseStream`, Claude uses the local CLI with Bedrock |
| AgentCore microVM → Bedrock | Runtime-role model invocation permissions; OpenAI uses SigV4 `ConverseStream`, Claude uses the CLI/SDK Bedrock path |
| Index host → Secrets Manager / local credential files | Instance role can read and create/update secrets under `source-truth/*`; it cannot delete them. Git token material is written to root-controlled files under `/opt/idx` with `umask 077` |
| Deployment workstation → AWS APIs | Operator credentials; potentially high privilege and outside this sample's enforcement boundary |
| Build/deploy → external package and release sources | npm/PyPI/NodeSource/GitHub upstream availability and integrity; exact versions, lock files, checksums, and repository signatures reduce but do not eliminate supply-chain risk. NodeSource signing-key retrieval is HTTPS-authenticated but the key bytes are not independently checksum-pinned |
| Answer → Feishu/Lark recipients | Source-derived content becomes visible to chat members; tenant/chat authorization is an operator responsibility |
| Multiple projects on one index host | Logical roots, manifests, per-repository locks, and tool routing; a host/root compromise crosses project boundaries |

## 6. Threat analysis (STRIDE)

| ID | Category | Threat | Existing controls | Residual risk / required handling |
| --- | --- | --- | --- | --- |
| T1 | Spoofing | Forged chat events or bot actions | Feishu/Lark SDK connection and app credentials from Secrets Manager; self-message guard; event deduplication | App-secret compromise enables impersonation; rotate secret and restrict app scopes |
| T2 | Spoofing | Unauthorized caller reaches index bridge | `http_bridge.py` binds `127.0.0.1` **by default**, but the deployed systemd unit passes `--host 0.0.0.0` explicitly (`activate_project.sh`, with the reasoning recorded there: uvicorn binds one address and the loopback `/health` probe is load-bearing). Every non-loopback bind emits a `bridge_unauthenticated_bind` warning at startup so the decision appears in the journal. A **second, in-process enforcement point** now admits only loopback and private/link-local peers and returns 403 otherwise (`peer_guard.py`, wrapped around the ASGI app ahead of session handling); `X-Forwarded-For` is deliberately ignored because the caller sets it. `BRIDGE_ALLOW_ANY_PEER=1` disables it for a topology fronted from outside the VPC, and logs that it did | **The bridge still has no application-layer authentication.** The peer check is authorization by network position, exactly like the security group — so it is defence in depth against an infrastructure misconfiguration, not a new kind of control, and any in-VPC principal that can route to the port is still admitted with full source-read access. Adding real auth requires a matching change in the agent's MCP client |
| T3 | Tampering | Agent or prompt injection modifies code | SDK built-in tools removed; disallowed write/exec tools; strict MCP config; server registers only a closed read-only tool list | A dependency/runtime compromise can bypass application controls; image and dependency integrity remain important |
| T4 | Tampering | Concurrent writers corrupt CodeGraph | Per-repository OS flock, systemd ordering, process restart guards, graph health checks | Host/root operator can bypass controls; recovery requires rebuild |
| T5 | Tampering | Malicious repository content steers the Q&A or glossary agent | Q&A exposes only the closed read-only MCP tool list. Claude glossary uses `--setting-sources ""` and denies Bash/Write/WebFetch/Task; OpenAI glossary exposes only batch-scoped paginated reads. Both constrain paths, reject credential-shaped output, and ground aliases against source | Repository content remains untrusted model input. Optional glossary is off by default and should be enabled only for approved repositories |
| T5a | Tampering | **Model output becomes model input**: a prior answer is replayed into the next prompt, so an instruction injected into answer *N* is read as trusted prior-turn context in prompt *N+1* | `followup-context.ts` wraps every replayed answer in an explicit `prior_answer trusted="false"` fence, announced ahead of the untrusted text, and strips the fence tag from replayed content so exactly one un-forged pair survives. `neutralizeMarkers` separately breaks forgery of the composer's own 【…】 structural markers | The fence is an instruction to the model, and instructions to models are advisory. The structurally stronger option — replaying a short factual summary instead of the full answer text — is **not** implemented, because it would degrade follow-up continuity, which is a core product behaviour. Answer integrity within one card chain is the exposed property; no credential or data leaves the system |
| T6 | Repudiation | Cannot correlate a harmful answer or admin action | Structured gateway logs, trace IDs, CloudWatch logs, VPC Flow Logs, deployment output | Logs are not a tamper-proof audit ledger; retention and access policy are operator choices |
| T7 | Information disclosure | Path traversal reads outside repository | `path_align` canonicalization, symlink escape checks, repo routing, withheld-path checks, extensive tests | A code defect or root compromise could bypass confinement; keep regression tests mandatory |
| T7a | Information disclosure | A containment check is given a root that bounds nothing (`--repo-root /`), making the glossary source-path confinement a no-op | `glossary_gen.py` rejects a filesystem root or top-level directory as `--repo-root`, and then **adopts the resolved path** for all downstream use. Validating the canonical path while continuing to operate on the original argument left a symlink-swap window: a link pointed at a safe directory passed the check and was re-resolved to `/` at the walk. `glossary_source.source_path()` retains its per-read confinement | Requires command execution on the index host with control over the generator's argv — a precondition that already confers the same file-read capability. What it removes is the attribution-evading path: contents read this way would be laundered into the shared glossary slice and published into chat |
| T8 | Information disclosure | Secret in source or host credential appears in answer/glossary/log | Credential-pattern refusal for glossary output; gateway best-effort redaction; user IDs hashed; repository path controls with credential files outside served roots; Feishu/Lark secret injected into the gateway environment rather than a credential file; Git token files created under `umask 077` | Pattern filters are incomplete by nature, and a host/root compromise can read the on-disk Git token. Do not store secrets in indexed repositories; run independent secret scanning before deployment/publication |
| T8a | Information disclosure | A secret split by leaked tool-call markup is re-joined **after** redaction and reaches the card | `sanitize-answer.ts` runs redaction last on **both** the body and the live evidence lane (order contract #2). The previously exempted evidence lane is fixed, and both lanes are pinned by a tag-split-secret test — the earlier evidence test used a contiguous secret and could not fail on the inversion. Correct ordering is necessary but **not sufficient**: the stripping step is gated by a markup detector, and that detector must recognise every tag the stripper removes. It did not — `<parameter>`, a closing-only `</invoke>` and a closing `</attempt_…>` were removed by the stripper but invisible to the guard, so the whole step became a no-op and the redactor saw only short fragments. The guard is now derived from the stripper's own tag set | Redaction remains pattern-based, so an unrecognised secret shape still passes. The ordering guarantee only holds for passes routed through this module, and the detector/stripper pair must stay in sync — a tag added to one without the other silently reopens this |
| T8b | Information disclosure | Internal identity/topology in logs: an assumed-role ARN and account id arrive in a backend error body and are logged | `redact.ts` adds ARN and keyed-account-id patterns alongside the existing 20+ credential shapes. The account-id rule is anchored to an account-id key on purpose: an unanchored 12-digit rule would redact the game-balance numbers this product exists to surface | An ARN discloses a role name and session-naming convention — reconnaissance value rather than a credential. Reading these logs already requires CloudWatch access in the account |
| T8c | Information disclosure | The agent container logs model-generated tool arguments, which derive from the user's question and can echo a pasted secret | `agent_lib.py` logs argument **shape** (`argChars`, `argKeyCount`) instead of values, matching the rule already applied to the prompt at run start. Key NAMES are not emitted either: an earlier version did, on the reasoning that keys come from the MCP tool schema — nothing enforces that, the dict is whatever the model produced, and a key like `secret-from-user-question` was logged verbatim. Value previews are opt-in via `LOG_TOOL_ARGS=1` | The container deliberately has no redaction primitive: not emitting a value is stronger than filtering it, and porting the gateway's pattern set would duplicate a control across two languages. Opting the previews back on re-opens the exposure |
| T9 | Information disclosure | Answer leaks proprietary code to unauthorized chat members | Bot only responds in configured tenant/chat context; output sanitization | Answers intentionally contain source-derived content. Chat membership and repository-to-chat mapping are explicit data-authorization decisions |
| T9a | Information disclosure | **Model-emitted markdown link, image or mention rendered clickable in the card**, giving a click-through (or, for an auto-loading image, no-interaction) exfiltration channel whose audience is the whole chat | `neutralize-links.ts` demotes links and autolinks to text, strips the image marker unconditionally, and removes model-emitted `<at …>` tags. Applied before redaction to **all three** markdown sinks: the live frames, the finalize re-render, and the reasoning panel (`redactSteps`) — the panel is a `markdown` element like the others and was initially missed. Nesting is handled by bounded iteration plus a postcondition sweep, because one pass over `[![a](i.png)](u)` produced a still-valid image. The fast-path discriminator covers every scheme the transform accepts (`ftp` was accepted by the transform but absent from the probe, so those returned unchanged). A fence exemption now requires a real closing fence | CardKit is a card renderer, not a browser DOM, so there is no script path. Images are neutralised unconditionally because whether CardKit auto-loads `![](url)` was not verified; that open question therefore does not affect the exposure. Fenced code remains exempt by design so quoted source is not corrupted — if CardKit linkifies inside fences, that region is exposed. Visible URL text is preserved so citations stay readable |
| T10 | Information disclosure | Model receives source content contrary to policy | Bedrock invocation is explicit, IAM-scoped, and documented; glossary opt-in | Repository clone locality is not data residency. Obtain approval for selected Region/model and repository classification |
| T10a | Information disclosure | The agent→index MCP channel carries repository source over **cleartext HTTP** inside the VPC | `agent_lib.py` validates the endpoint by scheme-and-host: loopback may use http (the `/health` probe depends on it), non-loopback http is accepted but emits a `codegraph_cleartext_transport` warning naming the exposure, and `CODEGRAPH_REQUIRE_TLS=1` makes it fatal. The loopback test classifies by **address**, via `ipaddress`, not by string shape: a prefix test also accepted `127.0.0.1.evil.com`, an attacker-controlled DNS name that was therefore treated as local and skipped both the warning and the TLS requirement. A DNS name is never resolved to make this decision, since a resolution result can change between check and connect | Cleartext is the **default** because the bridge terminates no TLS today, so requiring https would break every existing deployment while the control actually in force is VPC routing plus the index security group. Terminate TLS on the bridge and set `CODEGRAPH_REQUIRE_TLS=1` before production use |
| T11 | Information disclosure | Cross-project access on shared host | Per-project runtime, routing, repository roots, bridge project configuration, per-repo locks | Services and glossary jobs currently run with host-level privileges; host compromise can expose all projects on that instance |
| T11a | Information disclosure | The glossary build runs as **root** with read tools enabled over an attacker-influenceable repo, reaching the git credential and service env files | Three engine-side layers (`CC_DISALLOWED_TOOLS`, `--setting-sources ""` + `CC_DENY_READ_PATHS`, and the `_looks_like_credential` output filter), plus git handles stripped from the child env. Both transient-unit launch sites now add `InaccessiblePaths=` over the git token, askpass helper and git env files — an OS boundary that does not depend on the CLI honouring a flag | The mask is scoped to the credential files **by name**, not to `/opt/idx`: that directory is also the application root (`APP=/opt/idx/app`, plus `venv`, `bin/codegraph-server`, `glossary-envs`), so masking it wholesale would break the build. Running the build as a dedicated unprivileged user remains the real fix and needs a host migration |
| T11b | Information disclosure | The three VPC endpoints inherit the AWS default endpoint policy (`Principal:"*"`, `Action:"*"`, `Resource:"*"`), giving any in-VPC principal a network path to **any** ECR registry and **any** S3 bucket its IAM permits — the egress leg that composes with T11a and T2 | `provision_network.sh` attaches an endpoint policy conditioned on `aws:PrincipalAccount` to the **two ECR interface endpoints**, on create and on re-run (an endpoint made before this change is converged, and the convergence check compares the account id, not just the condition key). A failure to apply it retries and then **stops the deploy** rather than leaving an open endpoint behind a warning. The endpoint security group remains a separate and complementary control: it governs reachability, the policy governs authorized action | **The S3 gateway endpoint deliberately keeps the AWS default.** An ECR pull takes its manifest from ECR but its layers from `prod-<region>-starport-layer-bucket`, and that S3 request is not authenticated as a principal in the deploying account — a `aws:PrincipalAccount` condition there denies it, surfacing as a container that will not start rather than a legible AccessDenied. AWS's own documented minimum S3 endpoint policy for ECR keeps `Principal:"*"` and narrows Action/Resource instead. Narrowing S3 to `s3:GetObject` on the starport bucket is the correct next step but is unimplemented: it could not be verified against a real pull, and this deploy also stages artifacts in S3. `DEPLOY_VPCE_POLICIES=false` opts out of the ECR scoping too |
| T12 | Denial of service | Expensive/large queries exhaust bridge or model budget | Search result caps, file-size/row caps, timeouts, semaphore/session limits, glossary file cap, AgentCore timeouts | Authorized users can still create cost or load; deploy budgets/alarms and restrict bot membership |
| T13 | Denial of service | Glossary concurrency exhausts default host | systemd memory limits and opt-in glossary | Default concurrency can still oversubscribe small instances; tune `GLOSSARY_BUILD_CONCURRENCY` or use a larger host |
| T14 | Elevation of privilege | EC2 role permissions used after host compromise | Resource-name/account conditions; model-family scope; Secrets Manager prefix; no `DeleteSecret`; IAM validation tests | Role can create/update secrets under `source-truth/*` and invoke models. Shared-host compromise is high impact; isolate higher-sensitivity projects by account/instance |
| T15 | Elevation of privilege | `iam:PassRole` or policy attachment broadens privileges | Validation rejects unconditioned PassRole and unsafe AttachRolePolicy patterns; resource prefixes/conditions | Deployment identity is outside runtime controls and may still be highly privileged |
| T16 | Supply chain | Mutable Actions/packages/scripts execute attacker changes | GitHub Actions pinned to full SHAs; Claude Code `2.1.259` exact-pinned in both installation paths; npm lock integrity; base image digest; CodeGraph release checksum; explicit NodeSource signed repository; complete verified index-service transitive lock; version guards require matching pins | Python locks use exact versions but not artifact hashes. NodeSource signing-key retrieval and package downloads still depend on external HTTPS/repository infrastructure; compromise or artifact substitution remains possible |
| T17 | Destructive action | Teardown removes active resources or data | Teardown is a separate explicit command with dry-run/documentation; not called by install/deploy/tests | Operator error remains possible. Production use requires backups, change control, and stronger confirmations |

## 7. Existing security validation

The offline test entry point is `./scripts/test.sh`. It includes:

- repository/invariant checks;
- dependency/version drift checks;
- IAM policy validation;
- third-party manifest drift checks;
- shell, Python, and TypeScript unit tests;
- Python linting and TypeScript type/lint checks when dependencies are installed.

Release validation must additionally include:

1. Static and dependency scanning of the exact commit being released.
2. Critical findings reduced to zero; every warning resolved or explicitly dispositioned.
3. Secret scanning of tracked files and release artifacts.
4. Verification on ARM64 for the AgentCore image, CodeGraph binary, and complete index-service dependency closure.
5. Review of every externally downloaded executable and checksum/signature path.
6. Review of IAM and network diffs against the threat model.
7. Confirmation that no customer data, credentials, personal data, internal-only links, or private repository coordinates are included.

## 8. Open risks and release decisions

The following are not hidden defects; they are explicit decisions that an adopter must review before any production use. Items 1–3 were re-stated after a security review of this sample; the corresponding STRIDE rows carry the per-control detail.

1. **Unauthenticated index bridge:** there is still no application-layer authentication — network position is the whole authorization model. Two independent enforcement points now apply it: the security group, and an in-process peer check that admits only loopback and private peers (`peer_guard.py`, disabled by `BRIDGE_ALLOW_ANY_PEER=1`). The code default is a loopback bind and every non-loopback bind logs `bridge_unauthenticated_bind`, but the deployed unit passes `--host 0.0.0.0` deliberately. **Any in-VPC principal that can route to the port still gets full source-read access.** Adding authentication or mTLS requires coordinated changes to bridge and agent client.
2. **Shared privileged index host:** compromise can cross projects. The glossary build's transient units now mask the git credential, askpass helper and git env files via `InaccessiblePaths=`, and drop `CAP_SYS_ADMIN` with `NoNewPrivileges=yes` so a privileged process cannot simply undo its own mount namespace — but the build still runs as root, and the mask is scoped to those files because `/opt/idx` is also the application root. Higher-sensitivity workloads should use separate accounts/instances.
3. **Cleartext agent→index transport:** the MCP channel carrying repository source runs over http inside the VPC. This is now explicit rather than implicit: non-loopback http logs `codegraph_cleartext_transport`, and `CODEGRAPH_REQUIRE_TLS=1` makes it fatal. It remains the default because the bridge terminates no TLS today; terminate TLS on the bridge before production use.
4. **VPC endpoint egress scope:** the two ECR interface endpoints are conditioned on the deploying account instead of inheriting `Principal:"*"`, and a failure to apply that now stops the deploy rather than leaving an open endpoint. **The S3 gateway endpoint keeps the AWS default deliberately** — ECR fetches image layers from `prod-<region>-starport-layer-bucket` over that endpoint with a request that is not authenticated as a principal in the deploying account, so a caller-account condition there breaks image pulls as an opaque container-start failure. AWS's documented minimum S3 policy for ECR likewise keeps `Principal:"*"` and narrows Action/Resource; implementing that narrowing needs a real pull to verify and is left to the deployer.
5. **Python package hashes:** exact direct and transitive versions are committed, but Python artifacts are not locked with hashes.
6. **Proprietary Claude Code dependency:** version `2.1.259` is exact-pinned in the image and host paths, but use remains subject to Anthropic Commercial Terms and must be approved.
7. **NodeSource trust bootstrap:** apt verifies packages against the configured key, but the signing key itself is downloaded over HTTPS without a repository-pinned fingerprint/checksum.
8. **Optional glossary data flow:** source content is sent to Bedrock from the index host by either project-selected SDK; this must remain opt-in and data-policy approved.
9. **On-disk Git credential:** the read-only token is intentionally materialized in restricted `/opt/idx` files for unattended Git operations; host/root compromise exposes it, so scope and rotation matter.
10. **Pattern-based redaction:** the gateway redactor covers 20+ credential shapes plus ARNs and keyed account ids, and redaction now runs last on every sanitized lane — but pattern filters are incomplete by nature and an unrecognised secret shape still passes.
11. **Prompt-injection residuals:** replayed answers are fenced as untrusted and model-emitted links/images/mentions are neutralised, but a fence is an instruction to the model rather than an enforced boundary, and repository content remains untrusted model input throughout.
